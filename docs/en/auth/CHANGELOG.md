# Multi-user access domain — Changelog

Doc revision history for `docs/en/auth/`, seeded from the commits that introduced the feature.

## 2026-11-01

- **docs(auth): reconciled this domain with Google login + Gmail recovery (`2e8d62eb`).** Merging that PR into the account-administration branch collided in exactly one place — the `docs/en/auth/` file index — and left two claims untrue. The new page is numbered **05** now, because `04` was taken by [`04-google-login-and-email-recovery.md`](04-google-login-and-email-recovery.md). The *Recovery paths* section of [01](01-roles-and-invite-registration.md) said a member cannot self-reset and that upstream's `/forgot-password` is the only recovery: both changed. `POST /api/auth/email/forgot-password` + `/email/reset-password` issue a per-account, 15-minute, password-fingerprint-bound token, so members do have self-service recovery whenever a Gmail sender is configured; and `externalAuthRouter` now answers upstream's `/forgot-password` · `/reset-password` with **410 `email_recovery_required`** unless `legacyResetAllowed` (no `PUBLIC_APP_URL`, or the desktop build). The real remaining gap is the inverse of the old one: a hosted instance with no sender configured leaves a member with **no** recovery path at all. Mount table, `register.ts` and `auth-gate.tsx` line numbers re-anchored after the merge shifted them; `server/src/routes/auth.ts` is still byte-identical to `upstream/main`. Re-verified on the merged tree and the counts in [05's](05-admin-user-management.md#verification) verification bullet corrected with it: the `custom/` suites are now 6 files / 27 tests (their `external-auth*`, `gmail-mailer` and `google-identity` files joined), the client suite is 58 files / 459 tests, `check:i18n` still reports 60 locales / 1256 keys, and the server tree the merge leaves is 390 test files — a number only Linux CI can actually certify from this machine.

- **feat(auth): admin user management — new page [05-admin-user-management.md](05-admin-user-management.md).** `GET /api/admin/users`, `PATCH /:id/role`, `POST /:id/revoke-sessions`, `POST /:id/revoke-keys` in a fork-only router ([`server/src/routes/admin-users.ts`](../../../server/src/routes/admin-users.ts)) over a new [`server/src/services/users.ts`](../../../server/src/services/users.ts), mounted with `/api/admin/users` added to `ADMIN_ONLY_PREFIXES` ([`server/src/custom/register.ts`](../../../server/src/custom/register.ts)) — no upstream file gained a mount line. Dashboard `/users` page ([`client/src/custom/UsersPage.tsx`](../../../client/src/custom/UsersPage.tsx)) lists accounts with live key/session counts and two-click-confirm actions. Two invariants documented there: an admin cannot change their own role (which is also what guarantees at least one admin survives), and a role change needs no re-login because `validateSession` joins `users.role` per request. Not added, on purpose: create, delete, disable, and admin-changes-another-password.
- **docs(auth): re-anchored this domain after `ab5e6e79` moved the client and key services.** Every `#L` citation in [01](01-roles-and-invite-registration.md) and [02](02-user-api-keys.md) was resolved against the file it points into and the drifted ones corrected: `use-session.ts` `10→8` and `21→20`, the member key branch `KeysPage.tsx` `84→40` (now a `session.role === 'member'` ternary, not an `isMember` guard), the nav entries `261→266`, `/api/user`'s mount `register.ts` `41→44`, the register-form URL/submit anchors `auth-gate.tsx` `73→77` and `124→127`, and `services/user-keys.ts` `143→135` / `133→126` (the file is 138 lines, so the old `143` pointed past EOF). Prose the same commit invalidated: doc 01 claimed "no `client/` test covers" the invite-register view — one now does, so the note is narrowed to the failure branch, which still has no client coverage; doc 01 also claimed no endpoint can promote or demote another user, which this branch's `/api/admin/users` makes false. Doc 02's inert-field list gained the fact that `validateUserApiKey` now reads `u.role` and `resolveAuth` still drops it, so an admin key and a member key remain indistinguishable on `/v1`.
- **docs(auth): correct the UI gap after `30de3e2b` landed on `main`.** That commit shipped the dashboard half of this domain — `client/src/custom/use-session.ts` (role from `GET /api/user/session`), `InvitesPage.tsx`, `MemberKeysView.tsx`, the `/?invite=CODE` register form, and a role-aware nav filter — so the "Gap: no role-aware UI" bullet in [01](01-roles-and-invite-registration.md) is no longer true and was replaced by the caveat that actually applies: nav filtering is cosmetic, `ADMIN_ONLY_PREFIXES` is the boundary. Added: a **Dashboard navigation** row to the role table, the register-URL entry point in the registration flow (with a test-coverage note that the entry above has since corrected), a `client/src/custom/` row in [OVERVIEW](OVERVIEW.md), and a pointer that `use-session.ts` is the only consumer of `/api/user/session` in [02](02-user-api-keys.md). Also corrected [OVERVIEW](OVERVIEW.md): `app.ts` carries **five** added lines against `upstream/main`, not two — the import, the `registerCustomRoutes(app)` call, and the two comment lines plus the blank around it (still zero modified lines). Server code and the mount table are unchanged.

- **Merging `origin/main` back in removed a second, duplicate gate.** `12aa82eb` had re-added `requireAdmin` inline on upstream's own mount lines in `app.ts` (eight references) after the Turso rollout silently dropped them. That mechanism and the `custom/register.ts` guard do the same job, so `app.ts` went back to upstream + 5 added lines and the guard is the single source of truth — the tripwire suite is what proves the gate still exists after deleting those inline arguments.

- **refactor(auth): move the fork's HTTP surface to `server/src/custom/`** — `POST /api/auth/register` + `GET /api/auth/validate-invite` moved from upstream's `routes/auth.ts` (now byte-identical to `upstream/main`) to [`server/src/custom/auth.ts`](../../../server/src/custom/auth.ts); admin gating, invite and user-key mounts moved to [`server/src/custom/register.ts`](../../../server/src/custom/register.ts), called from two added lines in `app.ts`. The `requireAdmin` guard is now an **app-level mount registered before** upstream's own `/api/keys` · `/api/settings` · … lines, because mutating the imported router singletons with `router.use()` appends the gate *after* the routes and silently never runs. New `GET /api/user/session` returns `{ email, role, userId }`, replacing the `role` fields the fork had injected into upstream's `/api/auth/status` · `/login` · `/me` · `/setup` responses.
- Docs updated to match: [01](01-roles-and-invite-registration.md) gained a rewritten **Exact mount table** and a `surface.test.ts` tripwire entry under *Verification*; [02](02-user-api-keys.md) lists `/api/user/session`; [OVERVIEW.md](OVERVIEW.md) gained *Where the fork's wiring lives*.
- **Behaviour unchanged for clients**, with one exception: `role` is no longer present on the four upstream auth responses — read `GET /api/user/session` instead. The tripwire was mutation-checked (commenting out `registerCustomRoutes(app)` makes `surface.test.ts` fail with `expected 200 to be 403`), and the full server suite is green: 385 files / 4775 tests.
